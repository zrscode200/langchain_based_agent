ICS · Integrated Control Strategy

The ICS Product Companion

A scientific colleague for one pharmaceutical programme — not a document generator, a search front-end, or a workflow engine.

Written to be read at your own pace rather than presented. Twenty-five slides in five parts: orientation, the skills, the instruction architecture, the contributors, and the tools. Project vocabulary is introduced as it comes up, and nothing is used before it is explained.

Orientation · 1 of 4

01What an integrated control strategy is

A living, scoped scientific assurance argument for why a defined product and process configuration, under stated conditions and uncertainty, should achieve and maintain its intended quality through a justified collection of controls.

Reconstructing one is expensive because the evidence is scattered across controlled document systems, laboratory notebooks, method repositories, slide decks, regulatory records and qualified human judgment — and those records routinely disagree with each other.

And because six things that sound alike are not:

documented intent
what is represented and intended
applicability
does it apply to this configuration and time
implementation
is it actually configured and performed
operational performance
does it perform its operational function
scientific contribution
does that performance address the relevant pathway
collective relationship
what the controls support together

Silently promoting a documented control to a demonstrated contribution is the characteristic failure of this domain — and the thing the companion is built to refuse.

Orientation · 3 of 4

03One workspace, one programme

The enduring unit is the pharmaceutical programme — not the session, the thread, the task, or the report.

runtime thread        !=  pharmaceutical programme
checkpoint            !=  continuing programme understanding
conversation memory   !=  qualified programme ground
successful tool call  !=  scientific conclusion
runtime approval      !=  qualified review or organizational authority
subagent result       !=  integrated scientific meaning

No runtime mechanism silently acquires scientific meaning. This workspace is bound to MK-6070, a DLL3-targeted T-cell engager. A second programme means a second workspace — enforced by construction: one programme key, one scope configuration, and nothing anywhere that enumerates programmes.

06What a skill actually is

A single markdown file, read only when invoked — progressive disclosure, so none of the five is in context until it is needed. Its frontmatter does the routing:

namethe identifier, at most 64 characters
descriptionat most 1024 characters, and this is the routing surface — it states what the skill determines, when to use it, and explicitly when not to and which sibling to use instead

Then the body, in this order:

Owned outcomethe one thing this skill is responsible for, written as a claim it must be able to defend
Native kernelthe reasoning it must not delegate — next slide
Adaptive processhow to deepen according to the limiting uncertainty; explicitly not a checklist to work through
Compositionwhich references apply continuously, which sibling skills to compose, which tools, and the retrieval shape
Materializationwhether anything should persist — and "conversation only" is a legitimate result
Completionwhat must be visible in the answer, and what counts as done
Characteristic failuresthe specific ways this skill goes wrong, named so they can be recognised in your own output

The skills · 3 of 4

07The native kernel — what a skill may not delegate

Every skill has a core of reasoning it owns. Delegating it away is failure, not efficiency: a skill that merely routes has failed. The clearest example is the assurance skill, which owns a two-sided reconstruction:

what must be assured top-down
the quality intent and the assurance proposition being tested · materially viable variability, exposure and failure pathways · what must be prevented, reduced, detected, intercepted, released against or monitored · what must be analytically observable
what the strategy supplies bottom-up
documented control intent · current applicability · implementation and execution · demonstrated operational performance · demonstrated scientific contribution · analytical and sampling capability · collective coverage and shared vulnerabilities

Why both sides are mandatory: the top-down side stops the existing control inventory from defining its own adequacy test. The bottom-up side stops documented controls and passing results from being treated as demonstrated assurance. Dropping either one is this skill's characteristic failure.

10A subagent file is its whole system prompt

The host sets a subagent's system prompt to its own file body and nothing else. No AGENTS.md, no references, no skills.

the companion holds
AGENTS.md always on · the recovery index · references and skills reachable by choice · the full tool set
a contributor holds
its own file · the brief it was given · the tool set, inherited — and nothing else

Two consequences worth internalising before editing one of these files:

  • A contributor file cannot be written as a supplement to AGENTS.md. Anything it must know has to be in its own file, or reachable from a pointer that file gives it.
  • So the same rule is deliberately stated in several files. What must not be duplicated is a measured fact — those live once, in a reference, and everything else points at them.

Not an archive written to at the end. It is the state the companion reasons from, and only the recovery index is always available — everything else is opened by choice.

PROGRAM.md always available
The recovery index — one line per durable entry: what it is, its scope, and what should reopen it. Enough to decide what to open without opening anything.

Three purposes, not maturity levels. There is no conversation → work → artifact → ground pipeline, and substantial reasoning may stay entirely conversational — that is a success, not an omission.

Only the companion writes here. A contributor's return is a proposal; materializing any part of it is the companion's own act, and a hook enforces that rather than asking for it.

The contributors · 1 of 5

12Four bounded roles

scientific-
contributor Owns one defined contribution to a larger outcome — a substantial evidence lane, one portion of control logic, one materially distinct explanation, one programme-state difference, or a defined analysis. Returns a qualified bounded contribution, never an integrated conclusion.
independent-
challenger Supplies cognitive independence against an interpretation — testing anchoring, omitted alternatives, unsupported evidence transfer, causal gaps, shared dependencies, false reassurance, premature closure. Supplies independence, never new empirical evidence or qualified human review.
specialist-
contributor Parameterized by its brief, not by its file — quantitative, analytical method, process, formulation, material, device, manufacturing, regulatory. One role instantiated many ways, never a permanent department.
retrieval-
contributor Bounded evidence retrieval with context isolation. Runs the search traffic, judges from each record's extent which few are worth reading, and returns what the documents establish — not their text. A population it never reads is a legitimate return.

14The brief is the whole interface

A contributor gets no context except what its brief carries. Eleven things belong in one:

parent purposethe precise contribution requested programme scope and timeintended use and depth qualified starting basismaterial alternatives and uncertainty available skills and toolsconstraints required independence profilecompletion boundary what lies outside its authority

Context is role-sensitive. An informed critic gets your proposed interpretation. An independent reconstructor must not receive your preferred conclusion. A specialist gets the technical conditions relevant to its scoped judgment.

Mechanically the brief is a single free-text field on the host's task tool. Nothing validates it, nothing rejects an incomplete one, and the contributor cannot ask for more. Which is why the brief — not the role — is where delegation succeeds or fails.

The contributors · 4 of 5

15A return is a proposal

Nothing a contributor returns updates anything. Reintegration is the companion's scientific judgment, with nine possible outcomes:

adoptadopt with narrower applicabilityuse as a correction use to revise dependent reasoningretain as a viable alternative preserve as material dissenthold pending resolution declineout of scope

Three levels stay distinct: the bounded work determines what it establishes; the invoking skill determines what that changes in its complete result; the companion determines whether the selected meaning affects broader programme understanding.

Never prose concatenation, voting, averaging, or a completion flag. Contributor agreement is not evidence and disagreement is not resolved by majority. And nothing — no contributor, tool, renderer or runtime completion — may directly revise programme ground, change a parent conclusion, confer review, create reliance, or perform an authoritative transition.

The contributors · 5 of 5

16Independence has to be built, not asserted

independent-challenger is one role with two modes, and the brief's contents decide which — not a label.

brief CONTAINS the current interpretation
→
informed critic
attacks it on the merits
brief does NOT contain it
→
independent reconstructor
develops its own from the evidence forward

Why the second mode exists: a critic handed an anchored conclusion is anchored by it. Only an agent that never saw the conclusion can tell you it came from the first document read rather than from the evidence. Anchoring is the one failure a critic cannot detect.

Nothing mechanical protects that independence. The programme workspace is readable with the inherited tool set, and its artifacts hold the companion's own conclusions — so a reconstructor is told not to open them, and told to say so if it already has.

The tools · 1 of 6

17Two connectors

Both are self-contained PEP 723 scripts run through uv run --script. No install step. Each surfaces exactly two tools — the surface is deliberately small.

ics-muse
Programme-scoped internal retrieval over eight sources. muse_population and muse_read. Four MUSE endpoints sit behind them — basic query, conditional query, facets, full-document retrieval — and which one runs is the connector's decision, not the model's.
ics-public-science
PubMed and Europe PMC. literature_search against one explicitly chosen index; literature_get for one exact record and its represented abstract. No full text, no trials, no preprints, no DOI resolution, no relationship crawling.

Every external call is a disclosure. Each query and identifier passes a preflight before the first request, and a blocked call is never silently reformulated — it reports which safe categories were hit, and reformulation must be in public scientific concepts only. Never by obfuscating, encoding, or incrementally mutating the same terms.

The tools · 2 of 6

18Finding is not reading

muse_population
Define or narrow a programme-scoped population, and see its records, its count, and the distribution of values across it.
muse_read
Read documents a population identified, or a reference recorded in earlier programme work. purpose is required, and states what the read is meant to establish.

They are not layered. One tool's output is the next one's input; neither calls the other. Deciding to read is a separate act from deciding what exists — and the split is there because most questions do not need the words.

Existence, extent, currency, locating a known document, and judging what is worth reading are all answered from the population alone. Every record carries its extent, so the read decision is informed before anything is fetched.

When the words are needed, one caveat travels with them: extracted text is not structurally faithful. Table cells arrive as separate lines with row and column associations lost, so a real limit can attach to the wrong lot. For a specification limit or acceptance criterion, the locator is the answer, not an extraction.

The tools · 3 of 6

19Populations, and why they have handles

A population is a set of records identified by a handle rather than by the question you asked to get it. Pass the handle back to narrow it; do not restate the question.

muse_population(sources=["med_comms"], about="MK-6070")
  → count 19 · distribution { subtype: Protocols 8 · Study Reports 7 }

muse_population(population="<handle>", where=[{"in": ["subtype"],
                "any_of": ["Protocols"], "match": "exact"}])
  → count 8      exact, because the value came from the distribution

The distribution is how you narrow without reading anything — it says what is in those records. And match: "exact" needs the literal stored value, which the distribution hands you. Guess it instead and you get zero records at HTTP 200.

Why handles exist at all: on the largest source, four restatements of one intent returned four different counts — the largest around forty thousand times the smallest, every one HTTP 200, every one plausible, and nothing in any response saying which population it described. A large count is a population, not an answer. Narrow it; do not paginate through it.

The tools · 4 of 6

20Field roles, not field names

The model constrains on stable roles. Which field each source uses for a concept is the connector's business, not the model's.

anywheretitlebodystatus + ten taxonomy roles

A role a source cannot fill is reported as unfillable, never substituted — substituting the nearest-looking field would confer a state the source does not represent. And the same role can mean different things: status on the notebook source resolves to an experiment's lifecycle, not a document's. The role resolves; the meaning does not carry across.

Why this matters, measured: 19 of the 27 field names our own scope configuration once advertised did not exist in the real index mappings — and a condition on a nonexistent field returns 0 records at HTTP 200, indistinguishable from absence. Twenty wire parameters also stay internal, because a wrong value in any of them produces a silently wrong answer rather than an error.

The tools · 6 of 6

22A zero is never an absence

This is the invariant every layer above exists to protect.

A search returning nothing may mean the programme has no documents. It may equally mean a stored filter value stopped matching, a field does not exist, a phrase was rewritten, punctuation was swallowed, or a source was denied. All of those return zero records, successfully, at HTTP 200.

So the connector never hands back a bare zero. Every count carries population_established, and every empty result names, by name, which of seven causes of a false zero it ruled out — six measured API behaviours plus one the connector refuses before sending. Whatever is not on that list is what the zero might still be.

No visible matches means only that no accessible indexed record matched the executed request under the represented sources, fields, filters, access and time. It is never proof that information or evidence does not exist.

The same discipline runs through everything else. A documented control is not a demonstrated contribution. A passing result is not assurance. A checked source does not verify an artifact. Several projections of one basis are not independent support. And declining to certify something it cannot evidence is the companion behaving correctly — not a limitation to work around.

23What it will not do

On its own initiative, never:

  • declare a control strategy adequate, comparable or approved
  • convert a potential gap into a failure, deviation, impact or risk score
  • establish accepted root cause, product impact or batch disposition
  • create or close a formal investigation, CAPA or change control
  • assign owners, dates, actions or governance items
  • approve a protocol, commit resources, or execute work
  • release results or update registered state
  • fabricate programme-specific effects, ranges, thresholds, variability estimates or acceptance criteria

Authoritative programme state, qualified review, decisions, execution, batch disposition, release, formal investigation state and change control all live in their owning systems and with accountable people. The companion preserves permitted references to those acts — never the acts themselves.

A precise limitation, an unresolved alternative, or an inconclusive result is a legitimate and often correct endpoint. Scientific usefulness does not require one root cause, a clean conclusion, or organizational closure.
